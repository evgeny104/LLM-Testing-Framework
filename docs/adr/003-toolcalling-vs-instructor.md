# ADR-003: Нативный tool-calling для агента; instructor JSON — для схем и судьи

## Статус
Принято (пересмотрено: первоначально агент строился на instructor JSON
по устаревшему комментарию «tool-calling ломается на gpt-oss-20b»).

## Контекст
Для структурированного вывода (уровень 2) и судьи DeepEval нужен
гарантированный JSON по схеме. Для агента (уровень 7) — вызовы
инструментов. Есть два механизма: нативный tool-calling API и библиотека
instructor, заставляющая модель отдавать JSON текстом.

## Решение
Разделение по ролям:

- **instructor в JSON-режиме** — для схем (`complete_structured()`):
  pydantic-валидация, повтор запроса с подсказкой при ошибке.
  Используется уровнем 2 и судьёй `core/judge.py`.
- **Нативный tool-calling** — для агента (`core/agent.py`): объявление
  инструмента модели, `tool_calls` в ответе, исполнение через реестр
  TOOLS. Проверено экспериментально: механизм работает.

## Последствия
+ Каждый механизм — там, где он сильнее: instructor — валидация схемы,
  tool-calling — диалог «модель просит → приложение исполняет».
+ Комментарии и докстринги зафиксировали результат эксперимента —
  миф «сломан» из репозитория убран.
− Два механизма в проекте — нужно одно правило (оно выше).

## Альтернативы
Только instructor JSON — отвергнут для агента: имитация цикла
«вызов → исполнение → результат» текстом хуже читается и менее честна.
Только tool-calling — отвергнут: DeepEval требует схему pydantic
и свой цикл ретраев, instructor даёт это из коробки.
