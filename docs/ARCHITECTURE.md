# Архитектура

Подробные схемы устройства фреймворка. Краткое описание уровней — в README.

## Поток одного теста

```
┌────────────┐  1. просит данные  ┌─────────────┐  2. complete()  ┌────────────┐
│   тест     │ ─────────────────► │  фикстура   │ ──────────────► │  Groq API  │
│ (проверка) │                    │ (подготовка)│   HTTP-запрос   │   (SUT)    │
└─────┬──────┘                    └──────┬──────┘                 └────────────┘
      │                                  │ 3. ответ (текст/JSON)
      │ 4. получает                      ▼
      │                            ┌─────────────┐
      │                            │    ответ    │ ◄── ур. 4: контекст
      │                            └──────┬──────┘     из mock_retriever
      ▼                                   │
5. assert: ответ правильный? ◄────────────┘
```

Что проверяет assert на каждом уровне:

- **Уровень 1** — regex по эталонам из golden dataset (`golden_cases.py`).
- **Уровень 2** — объект `LegalAnswer`, валидированный pydantic-схемой.
- **Уровень 3** — DeepEval-метрики; судья — `evaluation/judge_model.py`.
- **Уровень 4** — RAGAS Faithfulness: опирается ли ответ на найденный контекст.
- **Уровень 5** — повторные прогоны: стабильность при t=0, допуск при t>0.

Общий вызов модели — `clients/groq_client.py`: `complete()` для текстовых
ответов, `complete_structured()` для JSON по схеме (instructor, JSON-режим).

## RAG-пайплайн

Все уровни работают над одной базой знаний — тексты статей хранятся только
в `data/legal_corpus.py` (единый источник истины). Уровни 1 и 4 — два
сценария одного пайплайна: известный документ и поиск по корпусу.

```
                    ┌─────────────────────────────┐
                    │  data/legal_corpus.py       │
                    │  (единый источник текстов)  │
                    └──────────────┬──────────────┘
                                   │
           по ID (уровень 1)       │       retrieve top-k (уровень 4)
           ┌───────────────────────┴────────────────────────┐
           ▼                                                ▼
   ┌───────────────┐   контекст в system-промпт    ┌───────────────┐
   │  SUT (Groq)   │ ◄──────────────────────────── │ mock_retriever│
   └───────┬───────┘                               └───────────────┘
           │ ответ
           ▼
   ┌────────────────────────────────────────────┐
   │ Проверки:                                  │
   │  ур. 1 — regex по эталонам (golden_cases)  │
   │  ур. 2 — pydantic-схема LegalAnswer        │
   │  ур. 3 — DeepEval judge: галлюцинации      │
   │  ур. 4 — RAGAS Faithfulness на контексте   │
   └────────────────────────────────────────────┘
```

Golden dataset не дублирует тексты: кейсы хранят `article_id` — ссылку на
статью корпуса, а номер статьи извлекается из её текста. Эталон и контекст
всегда из одного источника.
